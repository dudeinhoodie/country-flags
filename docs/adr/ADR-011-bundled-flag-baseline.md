# ADR-011: Bundled flag baseline with over-the-air corrections

- Status: Accepted
- Date: 2026-08-10

## Context

A content release publishes one image per flag, and the client downloads it,
verifies its checksum and caches it on disk. Issue #82 made that path work at
all: the pipeline published SVG only, `UIImage(data:)` cannot decode SVG from
downloaded bytes, and every flag in the app drew the placeholder. The fix added
raster representations and taught the client to pick one it can render.

That machinery delivers bytes that almost never change. Measured on
`content/generated/fixture-v1`: 250 vector originals are 2.3 MB and the full
raster set (`@2x` and `@3x`) is 5.4 MB. Either fits in an application binary
without discussion.

Meanwhile nothing hosts those bytes outside production. `assetBaseUrl` is a
constant in the pipeline and `publishBundle` uploads only the JSON documents, so
a dev deployment would serve asset URLs nobody can fetch (#92). The client
cannot draw a flag in any environment we can actually stand up.

The obvious conclusion — ship the flags in the app and delete the delivery path
— runs into the reason the delivery path exists. Flags change: Libya in 2011,
Mauritania in 2017, Afghanistan in 2021, Syria in 2024-2025. Roughly one every
year or two. The domain already models this rather than treating it as an
exception: an asset carries `validFrom`/`validTo`, a learning card revision
carries `promptFingerprint` and `changeClassification`, `docs/04` states that a
technical asset replacement preserves learning-card progress while a material
flag change creates a new semantic card, and the deterministic test fixture
carries replacement variants specifically to exercise it. For an app whose
subject is flags, drawing a superseded one is a defect in the product, not a
cosmetic lag.

## Decision

The application ships the flags of one content release inside its own bundle,
and the release mechanism remains the way a flag is corrected.

- The app embeds the vector originals of a pinned `contentVersion` in its asset
  catalog. On iOS the catalog preserves vector data, so one file is sharp at
  every size and costs 2.3 MB rather than 5.4 MB.
- The client draws the bundled image when the checksum of the representation the
  release publishes matches the bundled one. Otherwise it downloads, exactly as
  it does today.
- The asset registry, the representation list and the per-representation
  checksums stay in the contract unchanged. They are what the client matches
  against, and what an update is delivered by.
- The bundled set is generated by the content pipeline and copied into the app
  at build time. There is no hand-maintained list of images, and a build cannot
  ship a set that no release ever published.
- The client never assumes the bundled set is complete. Content adds a country
  before the next app release does, so a missing entry is a download, not an
  error.

## Consequences

- The first launch renders flags with no network and no CDN, and the app keeps
  working offline from the moment it is installed.
- A flag correction reaches users without an App Store release and without
  waiting for review.
- Asset hosting stops being on the critical path for the client. #92 remains
  worth doing — the update path and the other platforms need it — but it no
  longer decides whether the app works at all.
- The raster representations added in #82 become the update path rather than the
  everyday one. The rule they were added for is unchanged: a downloaded asset
  must decode into an image, and the test that proves it stays.
- The application binary grows by about 2-3 MB.
- The client gains a lookup from a published checksum to a bundled resource.
  This is the only new moving part, and it is what keeps a stale bundled image
  from being drawn over a corrected one.
- Android and web may adopt the same pattern or keep downloading. The contract
  forces neither.

## Alternatives

1. **Keep downloading everything.** Correct, and what the code does today, but
   the client cannot draw a single flag until asset hosting exists in every
   environment, and every first launch waits on the network before it can show
   the thing the app is about.
2. **Bundle only, drop the download path.** The simplest option and the one
   originally proposed. Rejected: a flag correction would then require an App
   Store release, and the image on screen would silently disagree with the card
   revision and checksum the server published, which the progress rules are
   built on.
3. **Bundle raster instead of vector.** Rejected on iOS: the asset catalog
   renders the vector with preserved vector data, which is both smaller and
   sharp at any size. A platform without that capability can bundle raster
   without changing this decision.

## Revisit triggers

- The published catalogue grows to where shipping it is no longer negligible,
  on the order of tens of megabytes.
- Flags begin changing often enough that most launches download anyway, which
  would make the bundled baseline dead weight.
- A second client platform needs the same baseline and cannot share the build
  step, making the pipeline output the wrong place to generate it from.

## Addendum 2026-09-04 — the baseline covers free decks only

Paid decks ([ADR-019](./ADR-019-paid-deck-entitlements.md)) put content in the
catalogue that a user has not bought. The bundling step does not know that:
`ios/Scripts/sync-flag-assets.mjs` copies the assets of a content release into
`Flags.xcassets` keyed by checksum, with no notion of which deck an asset
belongs to. Left alone it would ship the European coats and the state flags
inside the free download, so the paid artwork would sit on every device before
anyone paid for it.

The baseline is therefore scoped, not abandoned:

- the bundled set contains only assets used by a card that belongs to at least
  one deck with `access.model = FREE`;
- `--check` fails in CI when an asset reachable only through a paid deck is
  present in the catalog;
- assets of a paid deck arrive over the existing download path once the account
  holds the entitlement, which is exactly the path this ADR kept alive;
- everything else here is unchanged: checksum matching, the correction flow and
  the reasons for bundling at all still apply to the free catalogue.

This is about not giving paid artwork away in a free binary. It is not a
protection against a modified client, and this ADR does not claim one.

## Addendum 2026-09-05 — paid delivery is private and deck-scoped

The existing stable public CDN path remains valid only for assets reachable
through a published FREE card and for representations deliberately selected as
public preview. An asset reachable only through an entitlement deck is uploaded
to a private storage namespace instead.

The client learns about a paid-only representation only from the guarded deck
cards response after `DeckAccessService` succeeds. That response supplies a
short-lived signed download URL and expiry; the downloaded bytes then live in
the account-scoped offline cache. The public Entity API, public manifest and
global content change feed never expose the private object key or unsigned URL.

This still is not DRM: a legitimate owner can access bytes delivered to their
device. The boundary prevents accidental unauthenticated distribution through
the app bundle, Entity API, change feed or public bucket.
