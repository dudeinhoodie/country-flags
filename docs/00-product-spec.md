# Продуктовое ТЗ: Country Flags

Статус: `Draft 0.1`  
Целевой первый релиз: iOS MVP  
Последующие клиенты: Android, web

## 1. Цель продукта

Приложение помогает пользователю запоминать флаги стран с помощью коротких сессий интервального повторения. Архитектура должна позволять без переделки аккаунтов, прогресса и группировок добавлять:

- гербы;
- столицы;
- валюты;
- очертания стран и положение на карте;
- регионы и субрегионы;
- языки, население и другие факты;
- обратные карточки, например «страна → флаг»;
- исторические данные и изменявшиеся флаги;
- новые мобильные и web-клиенты.

Продукт не должен быть привязан к одному виду карточки или к единственной классификации стран.

## 2. Термины

- **Географическая сущность** — страна, территория, регион, субрегион или иная географическая единица.
- **Учебная карточка** — конкретная проверка знания: например, «флаг Франции → название Франции». Обратное направление является другой карточкой.
- **Шаблон карточки** — правило формирования вопроса, ответа и дополнительных фактов.
- **Колода** — именованная подборка учебных карточек: «Европа», «Азия», «Популярные».
- **Сессия** — ограниченный набор уникальных карточек, выбранный для одного занятия.
- **Review** — один показ карточки и оценка ответа.
- **Состояние карточки** — данные интервального повторения: сложность, стабильность знания, срок следующего показа и история ошибок.
- **Текущий уровень освоения** — динамическая оценка колоды, которая может повышаться и понижаться.
- **Достижение** — навсегда сохранённый факт первого достижения условия.

## 3. Основные пользовательские сценарии

### 3.1 Первый запуск

1. Пользователь видит краткое объяснение продукта.
2. Пользователь может:
   - продолжить без аккаунта;
   - войти через Apple;
   - войти через Google.
3. По умолчанию выбирается язык интерфейса из системной локали.
4. Пользователь может сразу открыть рекомендованную колоду и начать сессию.

Регистрация не должна быть обязательной для просмотра каталога и локального обучения.

### 3.2 Выбор колоды

Пользователь видит:

- рекомендуемые колоды;
- континенты;
- субрегионы;
- редакционные подборки, включая «Популярные»;
- прогресс, текущий уровень и число карточек к повторению;
- размер колоды и краткое описание.

Одна страна может входить одновременно в несколько колод. Группировки не должны сводиться к одному полю `continent`.

### 3.3 Запуск сессии

1. Пользователь открывает колоду.
2. Приложение предлагает размер сессии из настроек: `5`, `10` или `20` уникальных карточек.
3. Пользователь может изменить размер только для текущей сессии.
4. Система формирует снимок сессии.
5. Приоритет отбора:
   - просроченные карточки;
   - карточки в изучении;
   - недавно ошибочные карточки;
   - новые карточки;
   - остальные карточки для поддержания знания.
6. Если в колоде меньше уникальных карточек, чем выбранный лимит, используются все доступные карточки.

Повтор карточки после `Again` не считается новой уникальной карточкой. Например, сессия на 10 карточек может содержать 13 показов.

### 3.4 Обучение

Базовый режим MVP:

1. На лицевой стороне показывается флаг без названия страны.
2. Пользователь мысленно называет страну и раскрывает карточку.
3. На обратной стороне показываются:
   - локализованное название страны;
   - флаг;
   - 1–3 дополнительных факта, настроенных шаблоном;
   - источник и год для изменяемых данных по запросу пользователя.
4. Пользователь оценивает ответ:
   - `Again` — не вспомнил или ответил неправильно;
   - `Hard` — вспомнил правильно, но с большим трудом;
   - `Good` — вспомнил правильно;
   - `Easy` — уверенный и быстрый ответ.
5. После оценки открывается следующая карточка.

Нажатие `Hard` не должно означать неправильный ответ. Подсказка при первом использовании должна объяснять разницу между `Again` и `Hard`.

### 3.5 Объективный режим проверки

В продукте различаются два дополняющих друг друга режима:

1. **Обучение / flashcard** — пользователь сначала вспоминает ответ, затем раскрывает карточку и сам оценивает результат через `Again/Hard/Good/Easy`. Этот режим лучше подходит для интервального повторения, но приложение не может проверить, что пользователь действительно назвал страну.
2. **Проверка / multiple-choice** — пользователь видит флаг и четыре названия, а приложение объективно фиксирует правильность.

Multiple-choice не заменяет flashcard: узнавание правильного варианта обычно проще самостоятельного воспоминания и допускает угадывание. Рекомендуется оставить flashcard основным режимом обучения, а multiple-choice использовать для контрольных сессий и объективных достижений.

Оба режима MUST входить в публичный MVP. Допускается реализовать их последовательно: сначала flashcard, затем multiple-choice до публичного релиза.

Требования к multiple-choice:

- вопрос с флагом и 4 вариантами ответа;
- один правильный ответ;
- три правдоподобных distractor из активного каталога; регион/визуальное сходство используются как versioned difficulty policy;
- исключение одинаковых и почти дублирующихся названий;
- уникальные локализованные display names либо явная редакционная disambiguation;
- сохранённые option IDs, порядок, seed и `distractorPolicyVersion` в snapshot сессии;
- фиксация правильности и времени ответа;
- отсутствие раскрытия ответа до выбора.

Запись результата:

- неправильный ответ сохраняется как `isCorrect=false`, scheduler rating `Again`;
- правильный ответ сохраняется как `isCorrect=true`, scheduler rating `Good`;
- `Hard/Easy` не выводятся автоматически только из скорости ответа;
- исходный `answerMode` и `responseTimeMs` сохраняются, поэтому в будущем mapping можно изменить без потери истории.

В будущем MAY быть добавлен текстовый ввод с поддержкой альтернативных названий, разных locale и допустимых опечаток. Это даст объективную проверку именно воспоминания, но требует отдельной логики нормализации.

Достижения в одиночном flashcard-режиме отражают самооценку пользователя. Публичные рейтинги или соревнования можно строить только на объективно проверяемых ответах.

### 3.6 Завершение сессии

Экран результата показывает:

- число уникальных карточек и фактических review;
- правильные/неправильные ответы;
- распределение `Again/Hard/Good/Easy`;
- время;
- новые и повторённые карточки;
- изменение освоения колоды;
- полученные достижения;
- предложение повторить ошибки или вернуться в каталог.

Незавершённая сессия может быть продолжена после перезапуска приложения.

### 3.7 Аккаунт и синхронизация

- Гостевой прогресс хранится только на устройстве.
- После входа гостевые review загружаются в аккаунт как события, а не как один итоговый процент.
- Один аккаунт может иметь несколько способов входа.
- Автоматическое объединение аккаунтов только по email запрещено: Apple может скрывать реальный адрес, а одинаковый email не является надёжным доказательством владения двумя идентификаторами.
- Привязка второго способа входа выполняется только внутри уже авторизованного аккаунта с повторным подтверждением провайдера.
- Пользователь может видеть активные устройства, выйти с текущего или всех устройств.
- В настройках должна быть доступна полная очистка прогресса отдельно от удаления аккаунта.
- Пользователь должен иметь возможность инициировать полное удаление аккаунта внутри iOS-приложения.
- Если подключаемый Apple/Google identity уже принадлежит другому аккаунту, автоматический merge запрещён; пользователь получает понятный конфликт и может переключиться на существующий аккаунт.
- Пользователь должен иметь возможность запросить машиночитаемый экспорт своих данных.

## 4. Колоды и классификации

### 4.1 Системные колоды MVP

- Все сущности утверждённого владельцем продукта каталога, включая частично признанные.
- Европа.
- Азия.
- Африка.
- Северная Америка.
- Южная Америка.
- Океания.
- Популярные.
- Сложные/часто путаемые — динамическая персональная колода.
- Ошибки — динамическая персональная колода.
- К повторению сегодня — динамическая персональная колода.

Состав определяется переданным владельцем продукта versioned JSON-каталогом, а не автоматически всеми ISO-кодами. Статус страны/территории хранится отдельно и не влияет на возможность включить сущность в обучение.

### 4.2 Типы колод

- `CURATED` — состав явно задан редактором.
- `TAXONOMY` — состав следует версии классификации, например UN M49.
- `DYNAMIC_USER` — вычисляется из прогресса конкретного пользователя.
- `CUSTOM` — пользовательская колода; не входит в MVP, но схема данных должна её допускать.

Состав и название «Популярных» должны быть версионированы. Нельзя полагаться на неописанный флаг `isPopular`.

### 4.3 Трансконтинентальные и спорные случаи

- Связь «сущность входит в группу» должна быть many-to-many.
- Должна поддерживаться одновременно официальная статистическая классификация и редакционная классификация продукта.
- В интерфейсе необходимо избегать утверждений о признании спорных территорий.
- Список «страны» и список «страны и территории» должны быть различимы.
- Изменение классификации не должно удалять историю пользователя.

## 5. Модель интервального повторения

### 5.1 Общие требования

- Планировщик скрыт за версионируемым интерфейсом.
- Для первого релиза backend использует FSRS-6 через versioned adapter над `ts-fsrs`, а не самодельную формулу процентов.
- Целевая удерживаемость по умолчанию — `0.90`; значение является серверной настройкой и может быть изменено после продуктовых тестов.
- Backend является источником истины для `dueAt` и состояния планировщика.
- Каждое изменение состояния имеет `schedulerVersion`.
- Parameters имеют отдельную `parametersVersion`.
- История review является append-only и позволяет пересчитать состояние после обновления алгоритма.
- Изменение алгоритма не должно переписывать исходные оценки пользователя.
- Обновление scheduler выполняется через canary, migration checkpoint и reconciliation поздних offline events.

Актуальное руководство Anki описывает FSRS как более точную альтернативу старому SM-2 и подчёркивает, что `Hard` означает успешное вспоминание с трудом, а не ошибку.

### 5.2 Режим без сети

- Загруженные колоды и обучение доступны без сети.
- Клиент сохраняет review в локальный outbox с уникальными UUID.
- При синхронизации сервер дедуплицирует события и возвращает каноническое состояние карточек.
- Клиент может локально повторить карточку в текущей сессии после `Again`, но не объявляет постоянный `dueAt` каноническим до ответа сервера.
- Клиент MAY вести optimistic scheduler projection для нескольких офлайн-сессий; после sync canonical backend state полностью её заменяет.
- Конфликтующие review с нескольких устройств не теряются.
- Внутри устройства порядок задаёт `clientSequence`; между устройствами используется нормализованное effective time с детерминированным tie-break.

## 6. Освоение и достижения

### 6.1 Разделение понятий

`currentMasteryTier` — текущее состояние и может понизиться при длительном отсутствии повторений.  
`highestAchievementTier` — максимальный когда-либо достигнутый уровень и не понижается.

Это разделение обязательно, иначе «вечное золото» перестанет отражать текущее знание, а понижение уже выданной награды будет восприниматься как наказание.

### 6.2 Предлагаемые уровни

- `NONE`
- `BRONZE`
- `SILVER`
- `GOLD`
- `PLATINUM`

Правила должны храниться на сервере как версионируемые определения, а не быть зашиты в iOS.

Предварительная модель для продуктовой проверки:

| Уровень | Покрытие колоды | Минимум успешных review изученных карточек | Успешность за последние 30 дней |
|---|---:|---:|---:|
| Bronze | 50% | 1 | 70% |
| Silver | 75% | 2 | 80% |
| Gold | 90% | 2 | 90% |
| Platinum | 100% | 3 | 95% и не более 10% просроченных |

Эти числа являются гипотезой, а не окончательной формулой. Для маленьких колод должны использоваться абсолютные минимумы review, чтобы нельзя было получить высокий уровень после нескольких удачных ответов.

### 6.3 Другие достижения

- первая завершённая сессия;
- серия дней обучения;
- 10/50/100 изученных флагов;
- все континенты открыты на Bronze или выше;
- серия правильных ответов;
- возвращение после перерыва;
- завершение сессии без ошибок.

Серия дней должна учитывать часовой пояс пользователя и иметь явно определённую границу дня. Изменение часового пояса не должно позволять искусственно удваивать дни.

## 7. Настройки пользователя

Синхронизируются с аккаунтом:

- размер сессии: `5 | 10 | 20`, по умолчанию `10`;
- язык контента;
- режим ответа по умолчанию;
- показываемые дополнительные факты;
- звуки и тактильная отдача;
- напоминания, локальное время и дни недели;
- целевая удерживаемость, если эта настройка будет открыта пользователю;
- настройка «сначала карточки к повторению».

Локальными для устройства остаются:

- разрешение уведомлений;
- системные accessibility-настройки;
- служебные параметры кэша;
- последний открытый экран.

## 8. Контент и источники

### 8.1 Идентификаторы и регионы

- ISO 3166 alpha-2/alpha-3 используются как внешние коды, но не как первичные ключи.
- Для частично признанных сущностей без официального ISO-кода используется стабильный редакционный `key`; неофициальный или user-assigned код не должен записываться в поле ISO.
- Внутренние первичные ключи — UUID.
- UN M49 используется как базовая иерархия географических регионов и субрегионов.
- Локализованные названия должны иметь источник и locale.
- Для переводов SHOULD использоваться Unicode CLDR с редакционными исключениями.
- Исходный формат каталога описан в [04-content-json-format.md](./04-content-json-format.md) и проверяется JSON Schema до импорта.

### 8.2 Изменяемые факты

Население, валюта, столица и другие факты нельзя хранить как безусловно вечные строки.

Каждый изменяемый факт должен поддерживать:

- тип;
- типизированное значение;
- дату или год наблюдения;
- период действия;
- источник и URL;
- дату импорта;
- статус публикации;
- локализованное пояснение.

Для населения рекомендуемый первичный источник — World Bank Indicators API с индикатором `SP.POP.TOTL`; интерфейс обязан показывать год значения.

### 8.3 Валюты

- Страна может иметь несколько действующих валют.
- Одна валюта может использоваться многими странами.
- Связь должна иметь период действия и признак основная/дополнительная.
- Код ISO 4217 хранится отдельно от локализованного названия и символа.

### 8.4 Медиа

- Флаги и гербы хранятся как отдельные версионируемые assets.
- Оригинальное соотношение сторон сохраняется; изображение нельзя растягивать до общего прямоугольника.
- Для каждого asset хранятся источник, автор/правообладатель, лицензия, URL лицензии, checksum и период действия.
- SVG предпочтителен как мастер-формат; клиенту могут отдаваться безопасные подготовленные SVG/PNG/WebP-варианты.
- Emoji-флаги не являются источником графики: отображение зависит от платформы и не покрывает все продуктовые случаи.
- Нужна проверка визуально почти одинаковых флагов и специальных правил для distractors.
- Техническая замена asset сохраняет progress; существенная смена официального флага создаёт новую learning card и сохраняет старую историю отдельно.

### 8.5 Версионирование

- Опубликованный контент имеет монотонную версию или change cursor.
- Клиенты получают только изменения после своей версии.
- Удалённый из текущего каталога контент помечается неактивным, а не физически удаляется, если на него есть история review.
- Карточка хранит версию шаблона, по которому была создана.
- Сессия фиксирует learning-card revision, asset checksum, варианты ответа и grading/distractor policy versions.
- Production content публикуется атомарным versioned bundle с JSON Schema, SHA-256, manifest signature, preview и rollback.

## 9. Feature flags и общая архитектура

### 9.1 Feature flags

Продукт MUST иметь модуль удалённого управления доступностью функций. OpenFeature зафиксирован как обязательный provider-agnostic API/SDK. Конкретный self-hosted control plane/provider пока не фиксируется.

Feature flags используются для:

- постепенного включения новой функции;
- включения по environment, платформе, версии приложения, locale или стабильной пользовательской когорте;
- быстрого выключения проблемной функции без выпуска новой версии;
- A/B-вариантов после появления согласованной аналитики;
- временной настройки простых параметров интерфейса/поведения.

Feature flags не используются как замена:

- авторизации и server-side permissions;
- подписок и entitlement;
- миграций БД;
- сохранённых пользовательских настроек;
- секретов;
- обязательного обновления клиента.

Клиентское скрытие кнопки не считается защитой. Если flag выключает серверную функцию, backend MUST также отклонять относящиеся к ней операции.

Архитектура:

- отдельный интерфейс/приложение управляет control plane выбранного сервиса;
- NestJS `FeatureFlagsModule` использует OpenFeature Server SDK, инкапсулирует provider и вычисляет flags для контекста;
- `/v1/app-config` отдаёт iOS уже вычисленный типизированный snapshot;
- iOS использует OpenFeature Swift SDK с нашим snapshot provider, немедленно применяет локальные defaults, кэширует последний успешный snapshot и обновляет его без блокировки запуска;
- vendor-specific SDK не импортируется feature-модулями приложения напрямую;
- подробный контракт задан в [05-feature-flags.md](./05-feature-flags.md).

MUST использоваться OpenFeature. Внутренние типизированные обёртки разрешены, но evaluation должен проходить через OpenFeature SDK/provider contract. Это оставляет возможность сменить control plane без изменения точек использования flags.

### 9.2 Общая архитектура

Рекомендуемый стек:

- API: NestJS, REST JSON, OpenAPI 3;
- основная БД: PostgreSQL;
- ORM: Prisma или TypeORM, окончательно выбрать до кодогенерации; рекомендация — Prisma;
- assets: S3-совместимое объектное хранилище + CDN;
- фоновые задачи: очередь только при появлении импорта/рассылок; Redis не обязателен для самого первого прототипа;
- iOS: Swift, SwiftUI, async/await, локальная персистентность;
- Android/web: клиенты того же `/v1` API.
- feature flags: OpenFeature SDK, заменяемый provider, backend evaluation, cached client snapshot.
- observability: structured logs, metrics и distributed traces через OpenTelemetry-совместимый экспорт;
- iOS diagnostics: OSLog, MetricKit и заменяемый crash/error reporting provider;
- product analytics: типизированные события через backend ingestion и заменяемый exporter.
- advertising: `NoOpAdvertisingProvider` в MVP, типизированные placements и eligibility; реальный SDK/provider подключается только после отдельного решения.

PostgreSQL выбран вместо отдельной MongoDB, потому что аккаунты, связи провайдеров, карточки, колоды, review, достижения и идемпотентная синхронизация требуют уникальных ограничений и транзакций. Гибкие поля контента могут храниться в `JSONB`, который поддерживает индексацию. Разделение на PostgreSQL и MongoDB на старте создаст лишние миграции, бэкапы и согласование данных.

### 9.3 Логирование, ошибки и аналитика

Продукт MUST различать:

- **логи** — техническая диагностика выполнения;
- **errors/crashes** — неожиданные ошибки, падения и зависания;
- **метрики** — агрегированные показатели здоровья и производительности;
- **traces** — путь запроса между компонентами;
- **продуктовую аналитику** — события пользовательских сценариев.

Эти потоки могут экспортироваться в разные сервисы и имеют разные правила privacy/retention. Аналитика не является источником истины для review, достижений или аккаунта.

Требования:

- backend использует structured JSON logs с `requestId`, `traceId`, environment, service и release;
- iOS использует `Logger`/OSLog с privacy redaction;
- iOS подключает MetricKit для crash, hang и performance diagnostics;
- неожиданные ошибки централизованно отправляются через заменяемый `ErrorReporting` adapter;
- продуктовые события перечислены в version-controlled schema registry;
- iOS отправляет analytics batch асинхронно и не блокирует пользовательский flow;
- event IDs обеспечивают идемпотентность;
- токены, email, provider subjects, свободный текст ответа и содержимое Keychain не попадают ни в один telemetry поток;
- удаление аккаунта учитывает профили/идентификаторы во внешних analytics/error providers;
- feature experiment создаёт exposure только при фактическом показе варианта;
- подробный контракт задан в [06-observability-analytics.md](./06-observability-analytics.md).

### 9.4 Опциональная реклама

Продукт MAY использовать рекламу после MVP. В MVP закладывается только provider-agnostic архитектура:

- iOS использует `AdvertisingProviding` и production-safe `NoOpAdvertisingProvider`;
- placements перечислены в version-controlled registry;
- глобальный и placement-level kill switch управляются feature flags;
- eligibility отдельно учитывает privacy/consent, возрастную/региональную policy и будущий `ad_free` entitlement;
- рекламный SDK не добавляется до выбора provider, privacy-аудита и отдельного ADR;
- активная учебная сессия всегда остаётся без рекламы;
- реклама не влияет на FSRS, mastery, правильность ответа и достижения;
- начальный допустимый режим — контекстная/неперсонализированная реклама без IDFA;
- ATT не запрашивается «на всякий случай» и не является условием доступа к core-функциям;
- подробный контракт задан в [07-advertising.md](./07-advertising.md).

Фактическое включение рекламы, конкретные placements, рекламная сеть и персонализация не подтверждены.

## 10. Нефункциональные требования

### 10.1 Производительность

- Первый полезный экран из локального кэша: SHOULD до 1 секунды на поддерживаемом устройстве.
- Ответ API без учёта загрузки assets: p95 SHOULD до 300 мс при штатной нагрузке.
- Начало сессии из загруженной колоды доступно офлайн.
- Assets отдаются через CDN и используют checksum/ETag.

### 10.2 Надёжность

- Повторная отправка review не создаёт дубль.
- Незавершённая сессия восстанавливается после закрытия приложения.
- Потеря сети не приводит к потере ответа.
- Бэкап PostgreSQL и проверка восстановления обязательны перед production.
- Цели MVP production: PostgreSQL `RPO ≤ 15 минут`, восстановление сервиса `RTO ≤ 4 часов`.
- Object storage, immutable content bundles и feature flag configuration входят в backup/restore runbook.

### 10.3 Безопасность и приватность

- Собирать только данные, необходимые для аккаунта и обучения.
- Не хранить пароли Apple/Google.
- Не считать email стабильным идентификатором.
- Не писать identity/access/refresh tokens в логи.
- Должны быть Privacy Policy, Terms и описанный срок удаления данных.
- Удаление аккаунта должно удалять или необратимо анонимизировать связанные данные, кроме обязательных по закону записей.
- Аналитика и crash reporting не должны отправлять ответы пользователя и идентификаторы без обоснования и раскрытия.

### 10.4 Accessibility

- Dynamic Type.
- VoiceOver.
- Достаточный контраст.
- Уровни не различаются только цветом: нужны подпись/иконка.
- Reduce Motion отключает или упрощает 3D-переворот.
- Название страны не должно озвучиваться VoiceOver до раскрытия ответа.

### 10.5 Локализация

- Архитектура MUST поддерживать несколько locale.
- MVP: русский и английский.
- Locale идентифицируются BCP 47 tags, например `ru`, `en`, `pt-BR`, `zh-Hans`.
- Название, короткое название, официальное название и допустимые альтернативы хранятся раздельно.
- Числа и даты форматируются на клиенте по locale.
- Добавление locale не требует новых колонок БД, изменения API или новой версии схемы карточек.

## 11. Границы релизов

### MVP

- каталог флагов;
- системные колоды;
- flashcard-режим;
- multiple-choice с четырьмя вариантами ответа;
- сессии 5/10/20;
- интервальное повторение;
- гостевой режим;
- Apple и Google вход;
- синхронизация прогресса и настроек;
- Bronze/Silver/Gold/Platinum;
- базовая статистика;
- русский и английский;
- офлайн-обучение для загруженного контента;
- удаление аккаунта.
- OpenFeature-based feature flag module с заменяемым provider, безопасными defaults и удалённым выключением функций.
- error/crash reporting, технические метрики и минимальная продуктовая аналитика.
- provider-agnostic advertising module с `NoOpAdvertisingProvider`; без реального рекламного SDK и показов.

### После MVP

- гербы, столицы, валюты и карты как отдельные типы вопросов;
- пользовательские колоды;
- ежедневные цели и расширенные уведомления;
- Android;
- web;
- семейные/учебные группы;
- публичные рейтинги только при наличии объективного режима;
- подписка и платный контент после отдельного анализа Store-политик.
- опциональная контекстная реклама после отдельного продуктового/privacy решения.

### Не входит в MVP

- социальная сеть;
- пользовательская публикация изображений;
- полноценная административная CMS;
- многопользовательские соревнования;
- генеративный контент без редакционной проверки;
- CloudKit или Google Drive как отдельная система прогресса.
- реальный рекламный SDK, персонализированная реклама и ATT-запрос.

## 12. Сквозные критерии приёмки MVP

1. Новый пользователь без аккаунта может выбрать «Европу», пройти 5 карточек, закрыть приложение и продолжить с сохранённым локальным прогрессом.
2. Пользователь входит через Apple или Google, после чего гостевые review синхронизируются без дублей.
3. Та же карточка, изученная в «Европе», отображает прогресс в «Популярных».
4. При `Again` карточка снова появляется в текущей или ближайшей сессии согласно правилам планировщика.
5. Повторная доставка одного `reviewId` не меняет статистику.
6. Изменение размера сессии сохраняется в аккаунте и приходит на второе устройство.
7. Без сети пользователь проходит загруженную сессию; после восстановления сети сервер принимает события и возвращает каноническое состояние.
8. Достижение выдаётся один раз, а текущий уровень может измениться отдельно.
9. Пользователь инициирует полное удаление аккаунта внутри приложения; активные сессии отзываются.
10. Контент с населением показывает значение вместе с годом.
11. Флаги разных пропорций отображаются без искажения.
12. Русская и английская локализации не требуют изменения схемы карточек.
13. При недоступности feature flag provider приложение запускается с кэшем или встроенными defaults; критический пользовательский flow не падает.
14. Выключенный server-enforced flag скрывает функцию на iOS и запрещает соответствующую backend-операцию.
15. Неожиданная backend-ошибка получает `requestId/traceId`, попадает в error reporting и не раскрывает stack trace клиенту.
16. iOS сохраняет analytics/error batch офлайн в ограниченной очереди и отправляет после восстановления сети без дублей.
17. Logout сбрасывает analytics identity, а удаление аккаунта запускает удаление связанного профиля у настроенных providers.
18. В telemetry отсутствуют access/refresh/identity tokens, email и свободный текст ответов.
19. Сборка без рекламного SDK проходит весь core flow через `NoOpAdvertisingProvider`, не показывает рекламу и не запрашивает ATT.
