# Реестр решений, рисков и отложенных вопросов

Статус: backend implementation baseline зафиксирован. Вопросы, явно помеченные «после MVP» или «перед production», не блокируют начало backend-разработки.

В таблицах указано рекомендуемое решение по умолчанию. Если решение не изменено явно, агент может использовать рекомендацию, но должен записать её в ADR/decision log.

## 2. Авторизация и «облако» на Android

Здесь важно разделить две разные задачи:

1. **Вход в аккаунт** — Sign in with Apple и Google Sign-In.
2. **Хранение/синхронизация прогресса** — собственный NestJS backend.

На Android прямым аналогом входа через Apple является Google Sign-In / Google Identity. Google Drive App Data технически может хранить данные приложения, но создаст отдельную платформенную ветку синхронизации и не решит общий web/iOS/Android account state. Поэтому:

- iOS: Apple + Google;
- Android: Google, при желании также web-flow Sign in with Apple для доступа к тому же аккаунту;
- web: Google + Sign in with Apple;
- все платформы получают единый user ID и прогресс через backend.

CloudKit имеет web API, но остаётся Apple-centric инфраструктурой и не даёт преимуществ для выбранного NestJS multi-platform backend.

## 3. Обучение и оценка

### 3.1 Что означает «правильный ответ»?

В self-rated режиме приложение не знает, что пользователь произнёс или подумал. Оно знает только выбранную оценку:

- `Again` → неправильный;
- `Hard/Good/Easy` → правильный с разной уверенностью.

Если достижения должны доказывать знание, нужен multiple-choice или текстовый ввод. Рекомендация:

- mastery личного обучения может учитывать self-rating;
- competitive achievements и рейтинги — только objective answers;
- UI всегда объясняет источник оценки.

### 3.2 Следует ли смешивать направления карточек?

«Флаг → страна» и «страна → флаг» — разные навыки и разные `learning_card`. Их состояния нельзя объединять. При добавлении столиц и валют каждое направление также становится отдельной карточкой:

- страна → столица;
- столица → страна;
- страна → валюта;
- валюта → страны.

### 3.3 Что означает размер сессии?

Рекомендация: число уникальных карточек, а не число нажатий. Повторы ошибок могут увеличить фактическую длину. Это нужно объяснить на итоговом экране.

### 3.4 Новые и просроченные карточки

Решение MVP:

- один умный смешанный режим;
- отдельная быстрая колода «К повторению сегодня»;
- расширенные лимиты после сбора данных.

### 3.5 Undo

Пользователь может случайно нажать неверную оценку. Решение: Undo не входит в MVP; UI защищается от double tap. Если Undo появится позднее, он моделируется отдельным compensating event и никогда не редактирует синхронизированный review.

## 4. Mastery, медали и мотивация

### 4.1 Текущая медаль против достижения

Нужно показывать две величины:

- текущий уровень знания может понижаться;
- максимальное достижение остаётся навсегда.

Если оставить только навсегда выданное Gold, оно быстро перестанет отражать память. Если отнимать достижение, пользователь будет чувствовать наказание за перерыв.

### 4.2 Формула требует проверки данными

Пороговые значения из общего ТЗ являются гипотезой. Перед production нужно проверить:

- насколько быстро пользователь получает Bronze;
- не требует ли Gold слишком много однообразных повторов;
- справедлива ли формула для колод из 10 и 100 карточек;
- как влияет добавление новых стран в существующую колоду;
- что происходит после длительного перерыва.

Правило должно иметь version и evidence, иначе после его изменения невозможно объяснить старые награды.

### 4.3 Streak

Неочевидные случаи:

- путешествие и смена timezone;
- переход на летнее время;
- review около полуночи;
- намеренная смена часов устройства;
- офлайн review, пришедший через несколько дней.

Сервер хранит UTC и user timezone, а продукт задаёт календарное правило. Для MVP не вводить жёсткие штрафы за потерю streak.

## 5. География и политика

### 5.1 Каталог не ограничивается ISO entries

Каталог включает список владельца продукта, в том числе частично признанные сущности. ISO 3166 остаётся внешним справочным кодом и может отсутствовать. В JSON необходимо явно указывать статус:

- суверенные государства;
- государства-наблюдатели;
- частично признанные государства;
- зависимости;
- территории без отдельного флага;
- Антарктику;
- исторические государства.

Исторические государства не входят в MVP и не добавляются в текущие колоды. Позднее они могут храниться отдельными сущностями с обычным географическим `type`, `status: historical`, периодом существования в `validFrom`/`validTo` и `includeInCountryCatalog: false`.

Редакционный stable key обязателен для каждой сущности и не меняется вместе с названием или признанием. Для каждой публичной колоды нужен описанный inclusion rule.

### 5.2 Континенты не всегда однозначны

Россия, Турция, Казахстан, Грузия, Азербайджан и другие случаи могут попадать в разные учебные классификации. Нельзя хранить `country.continent_id` как единственную истину. Используются many-to-many relations и именованная taxonomy.

### 5.3 Названия чувствительны к locale

Официальное, привычное и короткое название могут различаться. Некоторые названия и территории политически чувствительны. Нужны:

- locale;
- тип названия;
- источник;
- редакционные overrides;
- альтернативы для поиска и будущего текстового ответа.

### 5.4 Флаги меняются

Флаг должен иметь период действия. Если государство изменит флаг, старая карточка не должна бесследно превратиться в новую и испортить историю. Нужно решить:

- старый флаг становится исторической карточкой;
- новая карточка создаётся отдельно или обновляется существующая;
- как пересчитывается mastery.

Решение: техническая/эквивалентная замена asset создаёт revision той же карточки и сохраняет progress. Существенная смена официального флага создаёт новую `learning_card`, ссылается на предыдущую через `supersedesLearningCardId`, а старый review evidence сохраняется.

## 6. Данные и лицензии

### 6.1 Население без года вводит в заблуждение

Каждое число населения показывается с годом и источником. Нужно определить частоту обновления — рекомендация раз в год после появления новых данных.

### 6.2 Столица и валюта не всегда одиночны

Возможны:

- официальная и фактическая столица;
- несколько столиц с разными функциями;
- несколько валют;
- de facto currency;
- замена валюты;
- currency union.

Не хранить `capital: string` и `currency: string` как единственные поля.

### 6.3 Права на изображения

Государственная символика может иметь особый правовой режим, а конкретные SVG-файлы — автора и лицензию. До публикации нужен реестр:

- источник каждого файла;
- лицензия;
- требуемая атрибуция;
- разрешение коммерческого использования/модификации;
- дата получения.

Нельзя считать, что «флаг страны автоматически не защищён» во всех юрисдикциях и для любого файла.

### 6.4 Качество данных

Нужен автоматический и редакционный контроль:

- дубли кодов;
- отсутствующие переводы;
- битые assets;
- неверный aspect ratio;
- циклы регионов;
- колода без карточек;
- карточка без primary ответа;
- одинаковые варианты ответа;
- устаревший источник;
- конфликт периодов действия.

## 7. Офлайн и несколько устройств

### 7.1 Один и тот же флаг на двух устройствах

Пользователь может офлайн ответить на одну карточку на iPhone и iPad. Backend хранит оба события. Внутри устройства причинный порядок задаёт `clientSequence`; между устройствами — нормализованное effective time, затем `receivedAt` и UUID. Stale event запускает deterministic replay/reconciliation и не теряется.

### 7.2 Время устройства ненадёжно

Review хранит raw client time, estimated server time, canonical `effectiveOccurredAt`, `receivedAt` и `timeConfidence`. Невозможное будущее ограничивается server bounds. Время клиента полезно для офлайн-истории, но не даёт security-права и не продлевает streak безусловно.

### 7.3 Обновление состава колоды

Если в «Европу» добавилась новая карточка:

- completion может упасть со 100%;
- highest achievement остаётся;
- current mastery пересчитывается;
- UI объясняет, что появился новый материал.

### 7.4 Удаление скачанного контента

Нужно определить размер кэша и downloads UI. Рекомендация MVP:

- автоматически хранить каталог и assets недавно открытых колод;
- не удалять активную сессию;
- позже добавить явное «Скачать колоду».

### 7.5 Выход при несинхронизированном прогрессе

При offline logout нельзя одновременно гарантировать мгновенную локальную очистку и сохранение неотправленных review. Рекомендация:

- по умолчанию предложить синхронизацию и отменить logout при отсутствии сети;
- разрешить «Выйти и удалить несинхронизированные данные» только с отдельным явным подтверждением;
- не переносить pending review к другому аккаунту;
- при реализации отложенного account scope шифровать его и открывать только после повторного входа того же server user.

## 8. Уведомления

Решения:

- локальные или серверные push;
- напоминание по расписанию или при due cards;
- quiet hours;
- badge count;
- поведение после смены timezone.

Рекомендация MVP: локальное ежедневное напоминание, настраиваемое пользователем. Серверные push и точный due-based scheduling добавить позже. Не запрашивать notification permission на первом экране без объяснения пользы.

## 9. Монетизация, реклама и детская аудитория

Архитектурная возможность рекламы подтверждена, но сама реклама не подтверждена к выпуску. Зафиксировано:

- в MVP только `NoOpAdvertisingProvider`, placements registry и eligibility layer;
- рекламный SDK не добавляется «на будущее»;
- начальный допустимый режим — contextual/non-personalized без IDFA;
- активная учебная сессия остаётся ad-free;
- реклама не влияет на FSRS, mastery и достижения;
- global/placement flags по умолчанию выключены;
- ATT, consent, возрастная/региональная policy и будущий `ad_free` entitlement сильнее feature flag;
- полный контракт: [07-advertising.md](./07-advertising.md).

До фактического подключения остаётся выбрать:

- нужна ли реклама вообще;
- provider и поддерживаемые страны;
- конкретные placements/formats;
- frequency caps;
- contextual-only или отдельный сценарий персонализации;
- модель «убрать рекламу»;
- допустимы ли rewarded ads и что именно они дают;
- возрастную аудиторию и применимую privacy policy.

До добавления платежей необходимо решить:

- бесплатная модель, подписка или one-time unlock;
- что остаётся доступно после истечения подписки;
- семейный доступ;
- восстановление покупок;
- удаление аккаунта при активной подписке;
- StoreKit и серверная проверка entitlement.

Также нужно решить, ориентирован ли продукт на детей. Это влияет на:

- аналитику и рекламу;
- сбор персональных данных;
- возрастной рейтинг;
- parental gates;
- тексты Privacy Policy;
- требования магазинов и применимое законодательство.

Рекомендация: не заявлять приложение как детское до отдельного privacy/legal анализа.

## 10. Аналитика продукта

Полный контракт вынесен в [06-observability-analytics.md](./06-observability-analytics.md). До интеграции provider необходимо утвердить event taxonomy, consent и retention.

Полезные продуктовые вопросы:

- какая доля пользователей начинает первую сессию;
- сколько её заканчивает;
- оптимален ли размер 10;
- какие колоды выбирают;
- где чаще нажимают `Again`;
- возвращаются ли пользователи к due cards;
- как быстро получают Bronze;
- помогает ли objective mode;
- сколько гостевых пользователей связывают аккаунт.

Нельзя использовать аналитику как вторую базу индивидуального прогресса.

## 11. Администрирование контента

CMS не нужна для первого MVP, но нужно определить владельца данных. Минимальный процесс:

1. Version-controlled source files и JSON Schema Draft 2020-12.
2. Versioned bundle manifest с SHA-256 и signature metadata.
3. Import CLI.
4. Validation report.
5. Preview diff.
6. Review/approval.
7. Atomic publish content version.
8. Rollback manifest без удаления review.

Без такого процесса исправление одного неверного флага может случайно изменить колоды и прогресс.

## 12. Рекомендуемые решения для первой итерации

Если разработку нужно начать без дополнительного обсуждения, использовать:

- RU + EN;
- iOS 17+;
- guest + Apple + Google;
- NestJS + PostgreSQL + Prisma;
- S3/CDN для assets;
- self-rated mode первым этапом технического MVP;
- полноценный multiple-choice до публичного MVP;
- 10 карточек по умолчанию;
- backend FSRS-6 через pinned `ts-fsrs` adapter, desired retention 0.90;
- immutable scheduler definitions, parameters versions и migration checkpoints;
- multi-device ordering через client sequence + normalized effective time;
- versioned multiple-choice distractor snapshots;
- technical stimulus revision сохраняет progress, material flag change создаёт новую learning card;
- системные колоды и без пользовательских колод;
- Bronze/Silver/Gold/Platinum с versioned provisional rules;
- локальные напоминания;
- ежегодное обновление населения;
- UN M49 для основной таксономии плюс редакционные overrides;
- колода «Все» строго следует переданному JSON-списку; дополнительные фильтрованные колоды по статусам можно добавить отдельно;
- без MongoDB, CloudKit и Google Drive как хранилищ прогресса.
- feature flags через backend-evaluated snapshot и provider adapter; без прямой зависимости feature-кода iOS от конкретного сервиса.
- provider-agnostic error reporting и продуктовая аналитика; OpenTelemetry для backend traces/metrics, OSLog + MetricKit на iOS.
- advertising abstraction с NoOp provider; реальный SDK и показы не входят в MVP.
